# Judge validation

Every number on the leaderboard is a verdict from an LLM judge: for each of the 51 claims and each book, the judge decides whether the book states the claim (correct), states part of it (partial), misses it (missing) or asserts the opposite (contradicted), and the released verdict is the majority over five independent passes. This folder is the evidence for how good that judge is and how it was chosen. It holds the human labels the judges were measured against, the verdicts of every judge configuration we compared, the per-call outputs behind the summary table, and a kit so that anyone can label their own sample and score the current judge against it.

Judge v2 (Claude Haiku 5.5 with `../prompts/judge_v2_system_prompt.txt`, in use since 2026-10-21) was selected with this study. Judge v1 (Gemini 3 Flash Preview with the original prompt, used from 2026-08 to 2026-10-21) is the first row of the table. The study was run on 2026-10-16 to 2026-10-20.

How to read it. Each row is one judge configuration (a model and a prompt) run five times over the same 260 claim-book cells (300 were sampled from the 459 cells of the paper's three entries, stratified by the v1 verdict, and 260 of them were labelled; see The labels below); its verdict per cell is the majority of the five passes, ties to the worse label, exactly as the leaderboard scores. Kappa is Cohen's kappa between the judge and the human label on the binary the leaderboard uses, correct versus not correct; raw agreement is the share of cells where the two agree on that binary. The floor row is a judge that never says correct. Cost per verified submission is the configuration's mean cost per call in this study times the 765 calls of one verified entry (3 books x 51 claims x 5 passes), at the list prices of 2026-10-16 in `prompts/price_table.json`; the v1 row is estimated from the same model's calls under the V5 prompt because the August run logged no usage. Model status is as of the study. The table is generated by `kit/compile_table.py`; `results/table_full.md` has every configuration, the reweighted figures and the single-pass view.

The selected judge is called selected, not best. The pre-registered rule for the confirmation run was a paired bootstrap of the kappa difference on the same cells, and both intervals include zero:

| Comparison | Kappa | Difference | 95% CI (paired cell bootstrap, 10,000 resamples) | Cells with the same verdict |
|---|---|---|---|---|
| V5H6 versus V5, both Claude Haiku 5.5 | 0.663 versus 0.614 | +0.048 | [-0.012, +0.112] | 233 of 260 |
| V5H6 versus judge v1 | 0.663 versus 0.601 | +0.062 | [-0.034, +0.161] | 202 of 260 |
| V5 versus judge v1 | 0.614 versus 0.601 | +0.014 | [-0.090, +0.119] | 199 of 260 |

What the switch rests on is therefore: equal or better agreement with the human labels, a generally available model instead of a preview one, and about a tenth of the judging cost. The files are in `results/paired_bootstrap_*.json`.

A second run of the selected judge gives a lower number. The leaderboard rescore of 2026-10-21 ran the same model and prompt, five passes, over every entry; on these 260 cells its majority verdicts agree with the labels at kappa 0.625 (raw agreement 80.4%), against 0.663 for the study run. That difference is run-to-run noise of a five-pass majority on 260 cells, and it is the size of the gap between most neighbouring rows above. Reproduce it with `python scoring/judges/validation/kit/analyze.py --labels scoring/judges/validation/labels/labels.csv --judge-record judge_record.json`.

## Every figure here is in-sample

Prompt variants were compared, and the figures are reported, on the same 260 labelled cells, as the judge validations of MT-Bench, AlpacaEval, HealthBench, DeepResearch Bench, WebJudge and ResearchRubrics do; none of them holds out labels for prompt development. About 45 configurations were scored on these cells during prompt development (all of them are in `results/table_full.md`), so every agreement figure in this folder is in-sample and should be read as such; the labels are published so that anyone can repeat the check with fresh labels, which is what the kit below is for. One prompt family that carried per-claim notes in the judge prompt was withdrawn as label leakage during the study and is not listed anywhere here.

## The labels

The population is the 459 claim-book cells of the paper's three entries (Claude Code, Cursor and Codex CLI, three books each, 51 claims). 300 cells were sampled with seed 20261010, stratified by the v1 judge's majority verdict so that partial and missing cells are over-represented, with every cell on which the five v1 passes disagreed included. Books and cells were given opaque codes, the mapping was sealed, and the human read each book once and labelled its cells with the rubric the v1 judge used (`prompts/v1_system_prompt.txt`), blind to the entry and to the judge's verdicts, between 2026-10-11 and 2026-10-16. 260 of the 300 cells were labelled, 20 to 36 per book; the sampling record and the 40 unlabelled cells are in `labels/sampling.json`, and the labels, with the sampling judge's five votes per cell, in `labels/labels.csv`.

There is one rater, so a second labeller's agreement with the first is not known; the kit exists so that this can be measured. All nine books come from the three August entries, so no book written by a later system is in the sample.

## The judge configurations

Every candidate was run with the same claims, the same nine books, five passes, and the settings below, through the same study driver; each call's model string, parameters, prompt hash, token usage and cost were recorded. No provider returned a dated model snapshot, so the model strings in the table are the only version pin there is, together with the run dates (2026-10-16 to 2026-10-20) in `results/configurations.json`.

| Setting | Gemini rows | Claude rows | OpenAI rows |
|---|---|---|---|
| Surface | Gemini API | Amazon Bedrock | Amazon Bedrock |
| Reasoning | thinking level high | effort high | reasoning effort high |
| Temperature | 0 | not accepted by the API | not accepted by the API |
| Output cap, thoughts included | 32,000 tokens | 32,000 tokens | 32,000 tokens |
| JSON output | response MIME type | prompt instruction, brace parser | JSON schema |
| Parse failure | re-asked up to twice, then scored missing | same | same |

The v1 row is different: it is the paper's own judge record from August 2026, five passes with the release settings of the time (default thinking, temperature 0, output cap 10,000), whose votes are in `submissions/<entry>/judge_record_gemini-3-flash-preview.json`.

Prompt lineage, all files in `prompts/` except the selected one, which is the shipped `../prompts/judge_v2_system_prompt.txt`:

| Prompt | What it is |
|---|---|
| v1 | the release prompt: the rubric as four decision rules and a JSON schema |
| V1, V2 | v1 with rule sentences appended, written from the rater's documented standard (`prompts/variants_V1_V2.json`); GPT-6 Luna only |
| V3 | the rules rewritten into the rubric itself |
| V4 | V3 plus structure: list the relevant passages first, quote the passage for every rubric point, verdict computed from the per-point flags |
| V5 | hand-written; introduces the claim's main finding as the thing to rate, verdict from whether the book states it in full, in part or not at all |
| V6, V7, V9, V10 | hand-written variants of V5 (tighter rules; a global rule on reading the book as a map; a taxonomy of point kinds) |
| V5H1 to V5H8, V5R1 to V5R4 | rewrites of V5's rules section by a reflective loop (`reflect_loop.py`, our own script in the style of GEPA and RART: reflect on the disagreement cells, rewrite the rules, keep the best); Claude Sonnet 5.5 as the reflector; the H loop saw its failed rewrites, the R loop did not |
| V5H6 | round 6 of the H loop, the selected prompt |
| V5RL1 to V5RL6 | the same loop seeded on GPT-6 Luna |
| effortmax | the v1 prompt at the provider's maximum reasoning setting |

## What is in this folder

```
README.md                       this file
labels/                         the human labels and how they were drawn
prompts/                        every prompt in the full table except the shipped v2 prompt; the price table
results/
  votes.csv                     per labelled cell: the human verdict and every configuration's five votes
  configurations.json           per configuration: model string, prompt, settings, run dates, calls, cost, where its outputs are
  table.md, table_full.md       the summary table above and the full table (generated)
  results.json                  every statistic behind the tables (generated)
  paired_bootstrap_*.json       the three pre-registered comparisons
  curated_rows.json             which configurations the summary table shows, and how they are named
outputs/<configuration>/passK.jsonl
                                one record per judge call for the nine candidate rows of the summary table: the parsed JSON the judge
                                returned (passages, per-point quotes, main-finding rating, verdict, justification), the verdict used for
                                scoring, and the call's model id, timestamp, prompt hash, usage, cost and latency; 11,769 records
kit/                            the scripts: compile_table.py, paired_bootstrap.py, analyze.py, build_kit.py, rate_app.py,
                                merge_labels.py, votes_from_scorecards.py
```

Every number in the tables is recomputable from `labels/labels.csv` and `results/votes.csv` alone; the outputs folder is the audit trail behind the votes, for reading why a judge decided a cell the way it did. The v1 row's per-call outputs beyond the verdict were not kept in the public record.

## Label your own sample

The kit builds a blind sample from any entries on the board, serves the books and the claims side by side in the browser, and scores your labels against the judge that produced the entries' records. Thirty cells from two entries is about ninety minutes, most of it reading the two books once.

```bash
python scoring/judges/validation/kit/build_kit.py --out kit_out --entries claude-code-2.1.252 cursor-3.15.6 --n 30 --seed 1
python scoring/judges/validation/kit/rate_app.py --kit kit_out        # open http://127.0.0.1:8795/ and label; every label is saved at once
python scoring/judges/validation/kit/analyze.py --kit kit_out          # when you are done: agreement with the current judge, with a bootstrap CI
```

The kit is blind by construction: books and cells carry opaque codes and the mapping sits in `kit_out/sealed/`, which only `analyze.py` opens. Label with the rubric shown in the app. Pass `--judge-record judge_record_gemini-3-flash-preview.json` to `build_kit.py` to stratify on the v1 judge instead. `merge_labels.py` turns a finished kit into the `labels.csv` schema; if you send us that file in a pull request we will report the agreement between your labels and the published labels on the shared cells, which is the inter-rater number this folder is missing.
